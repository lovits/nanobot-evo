# NanoEvo marketplace Skills paired benchmark — 2026-08-04

## Conclusion

NanoEvo evaluated three marketplace Skills with 18 real LLM runs. Two evolved
versions passed the efficiency promotion gate and one was rejected.

- Across all three candidates, including the rejected regression, total tokens
  decreased by **6.25%** and tool calls decreased by **13.54%**.
- Across the two promoted Skills, total tokens decreased by **19.19%** and tool
  calls decreased by **24.62%**.
- `analyzer` was not promoted because both measured metrics regressed.

No fake provider, canned response, or non-LLM task execution was used. Every V0
and V1 answer was generated by `agnes-2.0-flash` through the configured HTTP(S)
proxy. The aggregation script is deterministic and only totals the captured
provider usage and structured tool-call records.

## Experimental setup

- Skills: `codebase-survey`, `source-code-analysis`, and `analyzer`.
- Repositories: Blinker, Flask, and Jinja at the commits pinned in
  `benchmark_repositories.json`.
- Comparison: each Skill was compared only with its own evolved version.
- Controls: same model, task prompt, tools, maximum tool iterations, and pinned
  repository commit; each run used a fresh session.
- Order control: V0/V1 execution order alternated by repository.
- Token metric: provider-reported prompt plus completion tokens.
- Tool metric: every attempted tool call recorded by `ExperimentCaptureHook`.
- Promotion rule: all six runs complete without an execution error, and the
  evolved Skill reduces both aggregate tokens and aggregate tool calls over its
  three repository pairs.

## What the experiment demonstrates

The useful result is not that every generated patch improves performance. It
is that NanoEvo can close the complete loop:

1. collect real tool-use trajectories;
2. ask an LLM reviewer to improve the existing `SKILL.md`;
3. preserve the resulting version and diff;
4. run controlled V0/V1 experiments on held-out repositories;
5. promote improvements and reject regressions.

The `analyzer` regression is evidence for the promotion gate: an LLM-generated
Skill patch can be syntactically valid and evidence-grounded while still making
the runtime less efficient.

## Resume-safe wording

> Extended nanobot with an evaluation-driven Skill evolution loop that records
> real execution trajectories, generates reviewable Skill patches, versions
> changes, and gates promotion using paired benchmarks. In 18 real-LLM runs
> across 3 marketplace Skills and 3 pinned Python repositories, the gate
> promoted 2/3 evolved Skills; accepted versions reduced aggregate token usage
> by 19.2% and tool calls by 24.6%.

## Limitations

- This is a pilot with one paired repetition per Skill/repository combination;
  it is not a statistically conclusive benchmark.
- LLM sampling remains stochastic even with the same model and prompt.
- The experiment measures efficiency. It checks completion and execution
  errors but does not claim a full semantic-quality benchmark.
- A stronger resume claim should repeat each pair at least three times and
  report confidence intervals.
